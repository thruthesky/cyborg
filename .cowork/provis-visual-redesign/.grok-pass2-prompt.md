## Overview

**Cyborg** — Flutter + Flame 으로 만드는 2.5D 아이소메트릭 액션 RPG **MMORPG** 다.
세계관은 "AI 로봇이 점령한 세계를 인간 사이보그가 되찾는다".

핵심 전제:

- **단일 공유 월드.** 매치별 인스턴스도, 분리된 스테이지도 없다. 플레이어는 세션이 아니라 **월드에
  접속한다.** 여러 사용자가 같은 월드에서 동시에 사냥하고, 서로의 존재·이동·전투가 실시간으로 보인다.
  PK 가 허용된다(파티원끼리는 예외).
- 백엔드는 **SpacetimeDB**(Rust 모듈, maincloud 의 `withcenter-cyborg`). 게임 서버 계층이 따로 없고
  DB 안에서 reducer·view 가 돈다.
- 월드는 **1 km × 1 km**(`kWorldSizeMeters = 1000`, 타일 1 m). 지면은 32타일 청크로 나뉘어
  `ui.Picture` 로 구워 캐시된다(`GroundLayer`). 서버 tick 24 Hz, AOI 기반 구독.
- 현재 단계: 계정·캐릭터 선택 관문, 실시간 멀티플레이 동기화(이동·전투·스윙 애니메이션), 파티·경험치
  공유, 리더보드, 자동사냥까지 동작한다. **게임플레이는 상당히 진행됐고, 남은 약점은 비주얼이다.**

### 이번 분석에서 네 AI 에게 시키려는 것

**`provis` 패키지를 활용해 이 게임의 비주얼(플레이어 캐릭터 + 게임 맵)을 다시 설계하는 것.**

사람이 요구한 것:

1. `provis` 를 git submodule 로 `./packages/provis` 에 추가 → **이미 완료됨**(분석 전에 오케스트레이터가
   수행). `pubspec.yaml` 의 `dependencies` 에 `provis: {path: packages/provis}` 로 등록도 **완료됨**
   (`flutter pub get` 통과 확인).
2. 그 패키지를 활용해 **멋진 PC(플레이어 캐릭터) 디자인**을 만든다.
3. 그 패키지를 활용해 **멋진 게임 맵 디자인**을 만든다.

⚠️ **따라서 분석의 대상은 "submodule 을 어떻게 추가하는가" 가 아니다.** 그 단계는 끝났다.
분석해야 할 것은 **"이미 붙어 있는 provis 를 이 게임의 어디에, 어떤 순서로, 무엇을 대체하며
집어넣을 것인가"** 이며, 구체적으로 다음 네 가지다.

- ① **PC 디자인** — 현재 자체 렌더러(`CyborgRenderer` 1,202줄 + `CyborgDesign` 313줄)를 provis 의
  `Artist`/`BuiltArtist`/`CharacterBuild`/`HumanoidSpec` + `paintSurface`(19종 `Finish`) 체계로
  어떻게 옮기는가. 전면 대체인가, 병행인가, 자체 렌더러를 남기고 provis 의 셰이딩만 빌리는가.
- ② **맵 디자인** — 현재 `GroundLayer`(청크 캐싱 데이터 플레이트) + `LevelMap`(구조물 배치) 에
  provis 의 `Prop` 계열(`TreeProp`·`RockProp`·`BuildingProp`·`WaterProp`·`MoundProp`·`GroundPatch`·
  `flora`)과 `paintIsoGround`·`paintScene` 을 어떻게 결합하는가.
- ③ **세계관 정합** — provis 의 기본 기물은 **판타지 자연물**(나무·바위·목조 건물·물웅덩이)이고,
  이 게임의 무대는 **"빛으로 가득 찬 데이터 공간"**(흰빛 플레이트 + 청록/마젠타 발광)이다.
  이 둘을 어떻게 화해시키는가 — 세계관을 조정할 것인가, provis 기물을 사이버 톤으로 재색칠할
  것인가, 어느 쪽이 "멋진" 결과에 이르는가. **이것이 이번 분석의 가장 중요한 판단이다.**
- ④ **비용과 위험** — 1 km 월드 · 다중 접속 · 24 Hz 서버 tick 환경에서 절차 렌더의 프레임 비용,
  기존 스냅샷 테스트(`test/cyborg_render_snapshot_test.dart` 등) 파괴, 서버가 들고 있는 외형
  식별자(`kind` 문자열)와 provis `CharacterBuild` 사이의 간극.

## Persona

**2.5D 아이소메트릭 게임의 아트 디렉션과 렌더 파이프라인을 함께 책임지는 시니어 그래픽스
엔지니어 겸 아트 디렉터.** 다음 세 관점을 동시에 갖는다.

1. **아트 디렉션** — 실루엣·색 대비·조명이 화면에서 실제로 무엇을 읽히게 하는지를 본다.
   "예뻐졌다"가 아니라 **"적과 아군이 0.2초 안에 구분되는가", "1 km 월드가 지루한 판이 아니라
   지형으로 읽히는가", "밝은 배경에서 캐릭터 실루엣이 죽지 않는가"** 로 판단한다.
   MMORPG 는 화면에 십수 명이 겹치므로, 단일 캐릭터의 아름다움보다 **군중 속 식별성**이 우선이다.
2. **렌더 파이프라인** — Flame `PositionComponent` 트리 · `ui.Picture` 청크 캐시 · 깊이 정렬 ·
   카메라 컬링이 지금 어떻게 짜여 있고, provis 의 `paintScene`/`IsoSceneComponent` 가 그것과
   어디서 충돌하는지를 본다. 프레임 예산(60 fps = 16.6 ms)을 숫자로 따진다.
3. **점진적 이행 설계** — 7,800줄 규모의 기존 시각 코드를 한 번에 갈아엎는 권고는 사고를 부른다.
   **무엇을 먼저 바꿔야 가장 큰 시각적 개선이 가장 적은 위험으로 나오는지** 우선순위를 매긴다.

## Instructions

1. **모든 주장에 `파일:줄` 근거를 붙인다.** 근거를 못 대는 추정은 `[추측]` 으로 명시한다.
   provis 쪽 근거는 `packages/provis/lib/...` 경로로 적는다.
2. **`packages/provis/` 는 실제로 읽을 수 있다. 반드시 열어 보고 답하라.**
   `packages/provis/README.md` 와 `packages/provis/lib/provis.dart`(공개 API 목록),
   `packages/provis/example/lib/` (실제 사용 예 — `screens/game_map.dart`,
   `characters/recruits.dart`, `characters/aldric.dart`) 가 있다.
   **README 만 읽고 API 를 상상하지 말 것.** 존재하지 않는 클래스·파라미터를 권고하면 그 권고는
   통째로 무효다. 클래스명·생성자 인자는 `packages/provis/lib/src/**` 의 실제 선언에서 확인한다.
3. **provis 패키지 자체는 수정 대상이 아니다.** 그것은 별도 저장소의 submodule 이다. 이 게임 쪽
   코드(`lib/**`)를 고쳐서 provis 를 쓰는 것이 원칙이다. provis 에 없는 기능이 꼭 필요하면
   "provis 에 추가가 필요하다"고 명시하되, 게임 쪽에서 우회 가능한 길을 먼저 제시한다.
4. **아이소 투영 규격이 서로 다르다는 사실을 전제로 판단한다.**
   - 게임: `kTileWidth = 128`, `kTileHeight = 64`(`lib/game/iso.dart`), 고도 1단위 = `kHeightUnit 56`.
   - provis 예시: `IsoView(tileWidth: 156, tileHeight: 78)`.
   둘 다 2:1 이지만 **절대 크기가 다르다.** 어느 쪽에 맞출지, 맞추면 기존 히트박스·이동속도·
   카메라 줌·AOI 반경에 무엇이 파급되는지를 짚는다.
5. **세계관을 함부로 버리지 않는다.** `lib/game/palette.dart` 의 톤("어두운 폐허가 아니라 빛으로
   가득 찬 사이버 스페이스")과 `GAME-DESIGN.md` 가 이 게임의 정체성이다. provis 의 판타지 기물을
   그대로 얹어 "숲이 있는 사이보그 게임"이 되는 것은 **정합성 실패**다. 다만 사람이 요구한 것은
   "멋진 디자인"이므로, 세계관을 **확장**해서(예: 데이터 공간에 자라난 이질적 구조물, 폐허가 된
   자연 구역) 정합성과 시각적 풍요를 동시에 얻는 길이 있으면 그것을 제시한다.
6. **MMORPG 전제를 잊지 않는다.** "혼자 볼 때 예쁘다"는 판정은 의미가 없다. 같은 화면에 원격
   플레이어 수십 명(`RemotePlayerEntity`)과 몬스터가 동시에 그려질 때 무슨 일이 생기는지로
   판단한다. 절차 렌더는 캐릭터당 비용이 스프라이트보다 크다 — 그 비용이 어디서 터지는지 짚는다.
7. **성능 주장은 숫자로 한다.** provis README 는 캐릭터 1인 200프레임 반복 렌더 실측(8방향 418 µs
   /360방향 284 µs)을 싣고 있다. 이 수치를 그대로 인용하되, **화면에 N명일 때**로 환산해
   60 fps 예산(16.6 ms)과 대조한다. 캐시(`ui.Picture`·`ui.Image` 굽기) 전략이 필요한 지점을 짚는다.
8. 게임 화면(HUD·인벤토리·리더보드)은 전부 **Flame `PositionComponent`** 다(Flutter 위젯이 아니다).
   단 캐릭터 선택 화면(`lib/auth/`)은 Flutter 위젯이다. 두 층을 혼동한 권고는 맞지 않는다.
9. **기존 시각 코드를 "지금이 옳다"고 전제하지 않는다.** 사람이 요구한 것은 개선이지 보존이 아니다.
   다만 **무엇이 깨지는지 명시하지 않은 교체 권고는 채택하지 않는다** — 특히 스냅샷 테스트,
   원격 플레이어 외형 동기화(`kind` 문자열), 캐릭터 선택 화면과 게임 내 외형의 일치
   (`CyborgRenderer` 를 양쪽이 공유하는 현재 설계)가 어떻게 되는지 반드시 언급한다.
10. **우선순위를 반드시 매긴다.** "이것도 좋고 저것도 좋다"는 답은 쓸모없다. 사람이 자는 동안
    오케스트레이터가 실제로 코드를 고칠 것이므로, **1순위부터 순서대로 실행 가능한 작업 목록**이
    나와야 한다. 각 항목에 (a) 건드리는 파일, (b) 시각적 이득, (c) 깨질 위험을 붙인다.
11. 주석과 문서는 **한국어**로 쓴다. 코드 식별자는 영문 그대로.
12. 서버 설계 원칙(`spacetimedb/src/lib.rs` 머리말)을 어기는 권고는 하지 않는다: 클라이언트를
    신뢰하지 않는다 · 모든 테이블이 비공개이고 클라이언트는 view 만 읽는다 · 시각은
    `ctx.timestamp`, 난수는 `ctx.random()`.

## 분석 원칙

1. **근거 우선.** 모든 주장에는 출처를 붙인다 — 작업공간 자료는 `파일경로:줄번호`, 외부 사실은 그
   근거를 명시한다. 근거를 못 찾은 주장은 반드시 `[추측]` 으로 표시한다. 표시 없는 추측은 최악의
   결함으로 간주된다.
2. **읽고 말하라.** 실제로 열어 확인한 내용만 사실로 진술한다. 존재하지 않는 파일·함수·용어·수치를
   지어내지 말라(환각 금지). 확인 못 했으면 §6 에 "미확인" 으로 남긴다.
3. **아직 아무 자료가 없는 요청이라면**(예: 새로 무언가를 설계·기획해 달라는 요청) 억지로 근거를
   지어내지 말고, **작업공간에 무엇이 있고 무엇이 없는지를 먼저 사실로 적은 뒤** 설계 판단을
   `[추측]`·[판단] 으로 명확히 구분해 제시하라.
4. **범위와 경계를 분명히.** 이 판단이 어느 영역에 속하는지 명시한다(예: 어느 계층·어느 단계·누구의
   결정 권한인지). 한쪽만 바꿔서 되는지, 양쪽을 함께 바꿔야 하는지가 결론을 바꾼다.
5. **이 작업공간의 실제 제약을 반영.** 지침 문서와 자료에서 읽어낸 제약(대상 사용자·품질 기준·분량·
   기한·호환성·안전 규칙·검수 절차 등)을 무시한 이상론을 쓰지 말라. 실행 불가능한 권고는 권고가 아니다.
6. **모르면 모른다고 하라.** 억지 결론보다 "무엇을 더 봐야 하는지" 가 낫다.

아래 **"1차 분석 결과"** 는 방금 당신이 같은 질문에 대해 작성한 보고서다. 이제 당신의 임무는

**자기 글이라고 봐주지 말라.** 남이 쓴 허술한 보고서를 리뷰한다고 생각하라. 시간은 충분하다 —
다른 AI 들이 아직 돌고 있다.

### 1) 먼저 공격하라 (이 단계를 생략하지 말 것)

1차 보고서의 **모든 주장** 에 대해 따진다:

- **근거가 실재하는가?** 인용된 `파일:줄` 을 **직접 다시 열어라.** 파일이 없거나, 줄 번호가 엉뚱하거나,
  내용이 주장과 다르면 그 주장은 **삭제** 한다. (AI 는 그럴듯한 경로를 지어낸다 — 당신도 예외가 아니다)
- **근거가 결론을 지지하는가?** 자료가 존재한다고 해서 그것이 그 결론을 뜻하지는 않는다. 논리 비약을
  찾아라.
- **반대 증거를 무시했는가?** 결론과 어긋나는 자료가 어딘가 있을 것이다. 찾아서 열어라.
- **놓친 가설이 있는가?** 1차에서 세우지 않은 4번째 설명은 없는가? 특히 1차가 한 가설에만 매달렸다면
  거의 확실히 있다.
- **경계를 틀렸는가?** 한쪽 영역의 문제라고 했는데 실은 다른 쪽이 권위인가? 이 판단은 자주
  뒤집히고, 뒤집히면 권고 전체가 무의미해진다.
- **이 프로젝트의 실제 제약을 어겼는가?** 시스템 프롬프트(`.cowork/cowork-prompt.md`)와 자료에서 읽어낸
  제약(대상 사용자·품질 기준·분량·기한·호환성·안전 규칙·검수 절차 등)을 무시한 권고는 실행 불가능한
  이상론이다. 특히 시스템 프롬프트에 명시된 금지사항을 어긴 권고는 그 자체로 실격이다.

### 2) 구멍을 자료로 메워라

공격으로 드러난 빈틈은 **추측으로 메우지 말고 파일을 더 열어라.** 1차에서 안 본 파일을 최소 몇 개는
새로 열게 된다. 그러지 않았다면 공격이 무른 것이다 — 다시 공격하라.

### 3) 다시 써라 (복붙 금지)

최종 보고서는 1차보다 **명백히 나아야** 한다:

- 반증된 주장은 **뺀다**(고쳐 쓰지 말고 뺀다).
- 살아남은 주장은 **더 강한 근거** 로 뒷받침한다.
- 새로 발견한 것을 넣는다.
- 1차와 결론이 **바뀌었다면 바뀐 대로** 쓴다. 1차를 방어하려 들지 말라 — 틀린 결론을 지키는 것이
  이 작업의 최악의 실패다.

1차를 그대로 옮겨 적기만 한 보고서는 **실패** 다. 비판할 게 정말 없었다면, 그건 비판을 안 한 것이다.

그러므로 '어떻게 submodule 을 추가하는가' 는 분석 대상이 아니다. 분석할 것은 '이미 붙어 있는 provis 를 이 게임의 어디에, 어떤 순서로, 무엇을 대체하며 넣어서 멋진 PC 디자인과 게임 맵 디자인을 만들 것인가' 이며, 오케스트레이터가 사람이 자는 동안 곧바로 코드를 고칠 수 있을 만큼 구체적인 실행 순서(파일·함수·위험)가 나와야 한다.

### 세운 가설
1. **전면 대체** — 게임 시각 파이프라인을 provis `IsoSceneComponent` + `BuiltArtist`/`HumanoidRenderer` + `paintIsoGround` 로 통째 교체하면 “멋진 PC·맵”이 가장 빨리 나온다.

## 1. 결론 요약

**provis 는 이미 submodule·pubspec 에 붙어 있다** (`pubspec.yaml:42–45`). 남은 일은 “어디에 어떤 순서로 무엇을 대체하는가”이다.

### 한 줄 권고
**`IsoSceneComponent`/`IsoController`/`paintIsoGround` 로 게임 월드를 갈아끼우지 말고**, 게임의 `GroundLayer` + `IsoEntity` + `kind` 문자열 체계를 유지한 채, provis 의 **`paintSurface`·`Prop`·`BuiltArtist`/`HumanoidRenderer` 를 사이버 팔레트로 재색해 점진 이식**하라.

### 네 가지 핵심 판단

| # | 판단 |
|---|---|
| ① PC | **1단계** 기존 `CyborgRenderer` 경로에 `paintSurface`/`rimBand`/`Finish.metal`·`energy` 이식 → **2단계** `CharacterBuild` 두 종(`assault`/`infiltrator`) + `HumanoidRenderer` 로 **동일 API 표면**(`drawBody` 호환 래퍼) 교체. 전면 폐기와 병행이 아니라 **어댑터 뒤에 구현 교체**. |
| ② 맵 | `GroundLayer` 청크 bake **유지**. 그 위에(또는 bake 내부에) 사이버 재색 `Prop` 장식 레이어. `paintIsoGround` 전면 대체 **금지**. 데이터 타워(`BlockComponent`)는 게임 로직·충돌 권위 — provis `BuildingProp` 은 **비충돌 장식·랜드마크** 또는 타워 셰이딩 개선에만. |
| ③ 세계관 (최중요) | **세계관을 버리고 판타지 숲을 얹지 않는다.** 대신 이미 `WorldTree` 가 하는 것처럼 **“전산망 안에서 데이터가 응결·성장한 지형”으로 확장**. 나무=데이터 수관(민트/청록 발광), 물=콜로이드 풀(청록 반투명), 언덕=`MoundProp` 을 플레이트 융기, 바위=결정 파편. `BuildingProp(timber)` 중세 마을은 **정합성 실패**. |
| ④ 비용 | provis 실측 **캐릭터 1인 ≈ 0.28–0.42 ms/프레임** (README). 화면 20명 ≈ **5.6–8.4 ms**, 몬스터 30까지 합치면 **프레임 예산 16.6 ms 를 캐릭터만으로 잠식**. 청크 bake·거리 `detail`·원격 저상세 필수. |

### 우선 실행 순서 (오케스트레이터용 1줄 요약)
**맵 밀도(재색 Prop 청크 장식) → PC 셰이딩 강화 → PC Humanoid 어댑터 → 초상/스냅샷 동기 → (선택) 적 셰이딩.** 맵이 먼저인 이유: 밝은 빈 판이 시각 약점의 대부분이고, 서버 `kind`·전투 애니를 건드리지 않아 위험이 가장 낮다.

### 2.2 아이소 규격

| 타일 | `kTileWidth=128`, `kTileHeight=64` (`iso.dart:6–9`) | 기본 `IsoView(128,64)` (`iso_view.dart:16`); 예제만 150/156 |

| 월드 | 1 km, 청크 32 (`iso.dart:28–47`) | 예제 15×15 (`game_map.dart:166–168`) |

## 3. 원인 · 구조 분석

### 3.1 왜 “provis 를 붙였다”만으로는 안 되는가
provis 예제는 **자기 완결 미니 게임**(작은 격자 + 클릭 이동 + 기물 통행 차단)이다 (`game_map.dart:159–179`, `iso_scene.dart:84–133`). Cyborg 는 **서버 권위 MMORPG** 이고 시각은 Flame `world` 트리 안의 수많은 `IsoEntity` 가 각자 `render` 한다. 권위 계층:

| 계층 | 권위 | provis 역할 |
|---|---|---|
| 이동·전투·HP·kind | SpacetimeDB + 게임 시스템 | 없음 (건드리면 안 됨) |
| 그리드·충돌·청크 | `LevelMap` / `GroundLayer` | bake 보조 입력만 |
| 픽셀 | Canvas 렌더 | **여기가 이식 지점** |

### 3.2 세계관 충돌의 본질
- 게임 톤: 밝은 데이터 플레이트 + 청록/마젠타 (`palette.dart:5–9`, `GAME-DESIGN.md:52–66`).
- provis 기본 톤: 숲·흙·목조·자연 웅덩이 (`game_map.dart:235–325`, `TreeKind` 자연종 `tree.dart:14–35`).
- **화해 공식 (권고)**: 기물의 **형상 알고리즘**은 빌리고 **색·Finish·서사 이름**을 사이버로 덮는다.
  - `TreeProp(canopyColor: mint/cyan, barkColor: slate, kind: dead|pine)` → “데이터 수관 / 안테나 고사목”.
  - `WaterProp(color: 청록 반투명, reeds: false)` → “메모리 콜로이드 풀” (갈대 끄기 권장).
  - `GroundPatch(color: 옅은 청록 얼룩, blades: 0)` → 회로 오염 패치 (초록 잔디 금지).
  - `MoundProp` → 플레이트 융기 (지형을 “판”에서 “기복”으로).
  - `RockProp` → 결정/파편 (이끼 `mossy: false`).
  - `BuildingProp`: **timber/thatch 금지**. 필요 시 `WallStyle.stone` + `RoofStyle.flat` + 작은 랜드마크만. **파괴 가능 캐시·통행 차단 타워는 기존 `BlockComponent` 유지.**

이미 게임이 같은 화해를 `WorldTree` 에서 증명했다 (`world_tree.dart:14–16`).

### 3.3 PC 이행 구조
**문제**: `HumanoidRenderer` 는 골격·포즈·클립 체계이고, 현재 `CyborgRenderer` 는 자체 `_View`/`_Levels` + 블레이드 홀스터 + 임플란트 디테일이다. API가 다르다.

**권고 어댑터**:
```text
// 개념 (구현 지시용 — 이 보고서는 코드를 쓰지 않음)
CyborgRenderer.drawBody(...)  // 시그니처 유지
  → 내부가 HumanoidRenderer.paint(pose, yaw, light) 로 위임
  → 또는 Feature flag: useProvisBody
```
- `CharacterBuild` 매핑 초안:
  - `assault` → `Archetype.paladin` 또는 `berserker`, `Sex.male`, `armorHeaviness: 0.9`, `muscle: 0.85`, `hasPauldrons: true`, palette = `playerArmor`/`playerAccent`/`playerSkin` (`cyborg_design.dart:178–217` + `recruits.dart` oreb/vant 패턴).
  - `infiltrator` → `Archetype.assassin`, `Sex.female`, `armorHeaviness: 0.35–0.55`, `hairLength` 높음, kestrel 패턴 (`recruits.dart:362–383`).
- **무기**: 인게임 블레이드는 `showBlade` + `_renderBladeSwing` 이 별도 (`player.dart:1229+`, `remote_player.dart:452`). provis `WeaponKind` 와 이중으로 그리면 칼이 두 자루. **1차 이식에서는 provis 무기를 `WeaponKind.none` 또는 미장착에 가깝게 두고 게임 스윙 이펙트를 유지**하는 편이 안전.
- **조명**: 밝은 월드이므로 `LightRig.heroic`/`spectral` 을 그대로 쓰면 ambient 가 어둡다 (`shading.dart:91–113`). 게임 쪽 `LightRig` 래퍼 — key 차갑고 밝게, ambient 를 `skyLow` 쪽으로, rim 을 `playerAccent` 계열.

### 3.4 맵 이행 구조
```text
[유지] LevelMap 데이터 · 통행 · hazard
[유지] GroundLayer 청크 Picture (플레이트·도관·격자)
[신규] PropDecorLayer (또는 bake 확장)
        - 카메라 가시 청크의 PropInstance 목록
        - 청크 단위로 ui.Picture 에 paintProp 결과 bake
        - walkable props 만 (장식) → LevelMap 충돌과 이중 관리 금지
[유지] BlockComponent / WorldTree / SafeZoneField
```
- `IsoSceneComponent.addProp` 이 grid 를 block 하는 동작 (`iso_scene.dart:128–132`) 을 게임 `LevelMap` 과 병행하면 **반드시 어긋난다.** 장식 prop 은 `walkable: true` 이거나 충돌을 LevelMap 에만 둔다.
- `paintIsoGround` (`iso_stage.dart:125`) 은 작은 맵 전체 재도색용 — 1 km 에 매 프레임 호출 금지.

### 3.5 성능 숫자
| 부하 | 계산 | 예산 대비 |
|---|---|---|
| PC 1 | 0.28–0.42 ms (provis README) | 1.7–2.5% of 16.6 ms |
| PC 20 (원격 포함) | **5.6–8.4 ms** | **34–51%** |
| + 몬스터 30 (적 자체 렌더 유지 가정) | 적 비용 별도, 이미 enemy 1,243줄 절차 렌더 | 여유 거의 없음 |
| Prop 100개를 매 프레임 | [추측] 기물당 수십~수백 µs → 수 ms | 청크 bake 없으면 위험 |

**필수 완화**
1. Prop 은 `GroundLayer` 와 같이 **청크 Picture bake** (정적·저주기).
2. 캐릭터 `detail` 거리 감쇠 (`HumanoidRenderer`/`paint` 의 detail 인자).
3. 원격 플레이어: 화면 가장자리는 임플란트 생략·저 detail.
4. 정지 자세 방향 양자화 + `ui.Picture` 캐시는 선택 (연속 yaw 의 이점과 트레이드오프 — 게임은 연속 yaw 를 자랑함 `cyborg_renderer.dart:12–17`).

## 4. 반례 · 대안 · 한계

### 채택하지 않은 대안
| 대안 | 버리는 이유 |
|---|---|
| A. 게임 전체를 provis 예제 아키텍처로 이전 | §0 가설 1. 1 km·AOI·24 Hz 동기화와 비호환. |

| C. 판타지 숲·목조 마을을 “멋진 맵”으로 직수입 | 세계관 정합성 실패 (`palette`/`GAME-DESIGN`). |
| D. 셰이딩만 영원히 | 맵이 장판으로 남는 핵심 약점 미해결. |
| E. 서버에 CharacterBuild JSON 저장 | 서버 원칙·현재 kind 화이트리스트 범위 초과. 외형은 클라이언트 해석이 맞고 kind 만 권위. |

### 한계 · 리스크
- provis **휴머노이드 기본형은 판타지 장비 어휘**(헬름·망토·룬). `glowRunes: true` 는 회로처럼 읽히게 재색 가능하나, **사이보그 고유 임플란트(흉골 프레임 등)** 는 `HumanoidRenderer` 에 없음 → 손그림 `Artist` 오버레이 또는 게임 쪽 디테일 패스 필요 [1차 이후].
- `BuildingProp` 의 중세 단위(기와·초가)는 사이버 톤에 한계 → **데이터 타워는 기존 block 개선이 더 정합**.
- 적(`enemy.dart`) 은 이번 범위에서 2순위. 아군만 예뻐지고 적이 구식이면 식별성은 유지되나 톤 분열.
- provis 패키지 수정 금지(지침) — `Finish` 사이버 전용 추가가 필요하면 **게임 래퍼에서 색/LightRig 로 우회** 우선.

### 문서-코드 괴리
- `GAME-DESIGN.md` 방향 불리언 vs 실제 연속 yaw → 이행·리뷰 시 코드 우선.

## 6. 불확실 · 미확인

1. **Humanoid 1인 실측 418 µs** 가 이 머신·release/debug·임플란트 오버레이 포함인지는 이 환경에서 재측정하지 못함. 숫자 인용은 provis README 기준. **통합 후 DevTools 로 N=1,10,30 재실측 필요.**
2. **Prop bake 비용** — 기물 종류·detail 별 µs 미실측. 1순위 구현 직후 청크 bake 시간 로그 필수.
3. **provis walk/run 클립** 이 게임 대시·밀리 스윙 팔 각도와 얼마나 맞는지 — 코드 경로만 확인, 시각 대조 미실시.
4. **BuildingProp 을 사이버 색만으로 “데이터 센터”로 읽히는지** — 단위 텍스처가 돌/벽돌이라 한계 가능. 랜드마크 소량 A/B 필요.
5. **원격 플레이어 상한** — AOI 내 동시 렌더 인원 실측치 미확인. 성능 표의 N=20 은 설계 가정.
6. **`Finish.energy` + 밝은 배경** 에서 가산 블렌드(`shading.dart:637`) 과다 노출 여부 — 스크린샷 튜닝 필요.
7. 형제 게임 라리엔 비주얼 관례는 읽지 않음 (지시상 참고 가능하나 이번 범위에서 필수 아님).

### 가설을 가르는 다음 증거 (구현 단계에서)
- 1순위 Prop 장식만 켠 스크린샷 vs 현재 → “맵이 지루한 판인가” 판정.
- 2순위 셰이딩 후 최소 줌 0.275 스냅샷 (`cyborg_render_snapshot_test.dart:40–45`) → 실루엣 생존 여부.
- 3순위 어댑터 후 선택 화면/인게임/원격 나란히 → 정체성 일치 여부.
- N명 프로파일 → 가설 “Humanoid 전면이 예산 내”의 가부.
