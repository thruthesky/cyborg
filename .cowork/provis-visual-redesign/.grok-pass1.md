# provis 기반 Cyborg 비주얼 재설계 — 분석 보고서

## 0. 탐색 로그 (ToT)

### 세운 가설
1. **전면 대체** — 게임 시각 파이프라인을 provis `IsoSceneComponent` + `BuiltArtist`/`HumanoidRenderer` + `paintIsoGround` 로 통째 교체하면 “멋진 PC·맵”이 가장 빨리 나온다.
2. **셰이딩만 이식** — `CyborgRenderer`·`GroundLayer` 구조는 유지하고, provis `paintSurface`/`Finish`/`rimBand` 만 빌려 품질을 올린다.
3. **하이브리드 점진 이행** — 게임의 아이소 규격·청크 캐시·`IsoEntity` 깊이 시스템을 **권위로 두고**, provis 를 **재색·재질·기물 형상 엔진**으로 붙인다. 세계관은 “데이터 공간에 자라난 이질 구조물”로 **확장**하되 판타지 그대로 얹지는 않는다.

### 검증
| 가설 | 결과 | 근거 |
|---|---|---|
| 1 전면 대체 | **반증·폐기** | provis 예제 맵은 15×15 타일·`IsoSceneComponent` 단일 씬 (`packages/provis/example/lib/screens/game_map.dart:166–179`). 게임은 1006×1006 격자·32타일 청크 `ui.Picture` 캐시·구조물 스트리밍 (`lib/game/iso.dart:40–47`, `lib/game/level/ground_layer.dart:30–50`, `lib/game/action_rpg_game.dart:287–290, 1381+`). `IsoController` 는 게임 `ClickMoveLayer` 와 중복·충돌. |
| 2 셰이딩만 | **부분 지지, 단독 불충분** | 현재 PC 셰이딩은 `LinearGradient` 3~4단 (`cyborg_renderer.dart:49–81`). provis `Finish` 19종·`paintSurface` (`shading.dart:181–209, 274+`) 가 품질 상한이 높다. 그러나 사람 요구는 “멋진 PC·맵 **디자인**”이며, 지면은 여전히 단색 플레이트 합치기 (`ground_layer.dart:163–197`) — 셰이딩만으로는 맵 밀도가 안 오른다. |
| 3 하이브리드 | **채택** | (a) 아이소 기본값이 이미 128×64 로 게임과 같다 (`packages/provis/lib/src/iso/iso_view.dart:16`). (e) 서버 `kind` 는 `male_cyborg`/`female_cyborg` 두 문자열만 (`spacetimedb/src/character.rs:23`). |

### 가지치기
- **가설 1 폐기 이유**: 1 km MMORPG 스트리밍·Flame `priority` 깊이·서버 동기화 엔티티 트리 위에 예제 스케일 씬 컴포넌트를 얹는 것은 아키텍처 교체이지 비주얼 개선이 아니다. 시각 이득 전에 이동·AOI·블록 스트리밍이 깨질 위험이 크다.
- **“provis 기물을 기본 팔레트 그대로 숲/중세 마을로 배치” 폐기**: `palette.dart:5–9`, `GAME-DESIGN.md:52–66` 의 톤(“빛으로 가득 찬 사이버 스페이스”)과 정면 충돌. `BuildingProp` 기본 `WallStyle.timber` (`building.dart:14–16, 99`) 는 중세 마을 분위기.

## 1. 결론 요약

**provis 는 이미 submodule·pubspec 에 붙어 있다** (`pubspec.yaml:42–45`). 남은 일은 “어디에 어떤 순서로 무엇을 대체하는가”이다.

### 한 줄 권고
**`IsoSceneComponent`/`IsoController`/`paintIsoGround` 로 게임 월드를 갈아끼우지 말고**, 게임의 `GroundLayer` + `IsoEntity` + `kind` 문자열 체계를 유지한 채, provis 의 **`paintSurface`·`Prop`·`BuiltArtist`/`HumanoidRenderer` 를 사이버 팔레트로 재색해 점진 이식**하라.

### 네 가지 핵심 판단

| # | 판단 |
|---|---|
| ① PC | **1단계** 기존 `CyborgRenderer` 경로에 `paintSurface`/`rimBand`/`Finish.metal`·`energy` 이식 → **2단계** `CharacterBuild` 두 종(`assault`/`infiltrator`) + `HumanoidRenderer` 로 **동일 API 표면**(`drawBody` 호환 래퍼) 교체. 전면 폐기와 병행이 아니라 **어댑터 뒤에 구현 교체**. |
| ② 맵 | `GroundLayer` 청크 bake **유지**. 그 위에(또는 bake 내부에) 사이버 재색 `Prop` 장식 레이어. `paintIsoGround` 전면 대체 **금지**. 데이터 타워(`BlockComponent`)는 게임 로직·충돌 권위 — provis `BuildingProp` 은 **비충돌 장식·랜드마크** 또는 타워 셰이딩 개선에만. |
| ③ 세계관 (최중요) | **세계관을 버리고 판타지 숲을 얹지 않는다.** 대신 이미 `WorldTree` 가 하는 것처럼 **“전산망 안에서 데이터가 응결·성장한 지형”으로 확장**. 나무=데이터 수관(민트/청록 발광), 물=콜로이드 풀(청록 반투명), 언덕=`MoundProp` 을 플레이트 융기, 바위=결정 파편. `BuildingProp(timber)` 중세 마을은 **정합성 실패**. |
| ④ 비용 | provis 실측 **캐릭터 1인 ≈ 0.28–0.42 ms/프레임** (README). 화면 20명 ≈ **5.6–8.4 ms**, 몬스터 30까지 합치면 **프레임 예산 16.6 ms 를 캐릭터만으로 잠식**. 청크 bake·거리 `detail`·원격 저상세 필수. |

### 우선 실행 순서 (오케스트레이터용 1줄 요약)
**맵 밀도(재색 Prop 청크 장식) → PC 셰이딩 강화 → PC Humanoid 어댑터 → 초상/스냅샷 동기 → (선택) 적 셰이딩.** 맵이 먼저인 이유: 밝은 빈 판이 시각 약점의 대부분이고, 서버 `kind`·전투 애니를 건드리지 않아 위험이 가장 낮다.

## 2. 현재 상태 · 사실 관계

### 2.1 통합 준비 상태
- `provis: path: packages/provis` 등록 완료 (`pubspec.yaml:42–45`).
- 게임 쪽 `lib/**` 에서 provis import 사용은 **아직 없음** [탐색 기준: 게임 lib 은 자체 렌더만].

### 2.2 아이소 규격
| | 게임 | provis |
|---|---|---|
| 타일 | `kTileWidth=128`, `kTileHeight=64` (`iso.dart:6–9`) | 기본 `IsoView(128,64)` (`iso_view.dart:16`); 예제만 150/156 |
| 고도 | `kHeightUnit=56` (`iso.dart:15`) | `heightScale = tileWidth * squash / √2` ≈ **78.4** @128 (`iso_view.dart:37`) |
| 월드 | 1 km, 청크 32 (`iso.dart:28–47`) | 예제 15×15 (`game_map.dart:166–168`) |
| 깊이 | Flame `priority = (x+y)*100` (`iso.dart:84–86`, `GAME-DESIGN.md:159–167`) | `paintScene` 정렬 (`iso_scene.dart:47–65`) |

**결론**: 타일 절대 크기는 게임에 맞추고(이미 기본 일치), **게임 타일/줌/이동 상수를 156으로 올리지 말 것.** 히트박스·속도·카메라·AOI 파급이 전 밸런스로 번진다. props 그릴 때 `IsoView(tileWidth: 128, tileHeight: 64)` 를 쓰면 접지 투영은 게임 `gridToScreen` 과 동일한 2:1 식이다. 고도 스케일(56 vs ~78)은 **z 기물을 거의 안 쓰는 지면 장식에서는 영향 적음**; 건물 층고를 provis 로 그릴 때만 의식.

### 2.3 PC 렌더 공유 경로 (단일 진실)
```
CyborgKind (서버 id) → CyborgDesign → CyborgRenderer.drawBody
  ├─ Player._drawFrame          (player.dart:1218)
  ├─ RemotePlayerEntity.render  (remote_player.dart:435)
  ├─ CyborgPortrait             (cyborg_portrait.dart:12–14)
  └─ CyborgPreviewPainter       (cyborg_preview.dart:53)
```
- 서버: `CHARACTER_KINDS = ["male_cyborg","female_cyborg"]` (`character.rs:23`).
- 클라이언트 다리: `CyborgKind` (`cyborg_kind.dart:12–22`).
- 디자인: `assault` 키 108 / `infiltrator` 키 102, 진영색 청록 공유 (`cyborg_design.dart:178–268`, `palette.dart:79–87`).

### 2.4 맵 렌더
- `GroundLayer`: 타입별 Path 합쳐 단색 fill + 격자 + 도관 트레이스, 방화벽만 매 프레임 (`ground_layer.dart:153–208`).
- `LevelMap`: `TileType` floor/circuit/hazard/stream, `BlockType` wall/crate (`level_map.dart:10–34`).
- `WorldTree`: 이미 사이버 데이터 나무 (`world_tree.dart:9–16`).
- `BlockComponent`: 아이소 3면 큐브, 파괴/HP 로직 포함 (`block.dart:12–66`).
- 마운트: `GroundLayer` → `SafeZoneField` → `WorldTree` → player (`action_rpg_game.dart:287–298`).

### 2.5 provis 가 실제로 주는 것
- 재질: `Finish.metal`·`energy` 등 19종, `paintSurface` (`shading.dart:181–209, 274+`, energy 구현 `629–649`).
- PC: `CharacterBuild` → `HumanoidSpec` → `HumanoidRenderer` / `BuiltArtist` (`character_build.dart:38–115`, `built_artist.dart:47+`, `humanoid_renderer.dart:51+`).
- 맵: `Prop` 접지 원점 규약, `paintProp` 이 squash/grounded 처리 (`prop.dart:12–106`).
- 사이보그 예: `kestrelUnit` 등 청록 accent·`glowRunes`·`LightRig.spectral` (`recruits.dart:358–383`).
- 성능: 8방향 418 µs / 360방향 284 µs (`README.md:257–264`).

### 2.6 문서 vs 코드 불일치
`GAME-DESIGN.md:172–178` 은 캐릭터 방향을 `facesRight`/`facesDown` 불리언으로 설명하지만, 실제 `CyborgRenderer` 는 **연속 `yaw`** (`cyborg_renderer.dart:12–21`, `player.dart:1186–1189`). 이행 시 문서 서술이 아니라 **코드 계약을 따르라.**

## 3. 원인 · 구조 분석

### 3.1 왜 “provis 를 붙였다”만으로는 안 되는가
provis 예제는 **자기 완결 미니 게임**(작은 격자 + 클릭 이동 + 기물 통행 차단)이다 (`game_map.dart:159–179`, `iso_scene.dart:84–133`). Cyborg 는 **서버 권위 MMORPG** 이고 시각은 Flame `world` 트리 안의 수많은 `IsoEntity` 가 각자 `render` 한다. 권위 계층:

| 계층 | 권위 | provis 역할 |
|---|---|---|
| 이동·전투·HP·kind | SpacetimeDB + 게임 시스템 | 없음 (건드리면 안 됨) |
| 그리드·충돌·청크 | `LevelMap` / `GroundLayer` | bake 보조 입력만 |
| 픽셀 | Canvas 렌더 | **여기가 이식 지점** |

### 3.2 세계관 충돌의 본질
- 게임 톤: 밝은 데이터 플레이트 + 청록/마젠타 (`palette.dart:5–9`, `GAME-DESIGN.md:52–66`).
- provis 기본 톤: 숲·흙·목조·자연 웅덩이 (`game_map.dart:235–325`, `TreeKind` 자연종 `tree.dart:14–35`).
- **화해 공식 (권고)**: 기물의 **형상 알고리즘**은 빌리고 **색·Finish·서사 이름**을 사이버로 덮는다.
  - `TreeProp(canopyColor: mint/cyan, barkColor: slate, kind: dead|pine)` → “데이터 수관 / 안테나 고사목”.
  - `WaterProp(color: 청록 반투명, reeds: false)` → “메모리 콜로이드 풀” (갈대 끄기 권장).
  - `GroundPatch(color: 옅은 청록 얼룩, blades: 0)` → 회로 오염 패치 (초록 잔디 금지).
  - `MoundProp` → 플레이트 융기 (지형을 “판”에서 “기복”으로).
  - `RockProp` → 결정/파편 (이끼 `mossy: false`).
  - `BuildingProp`: **timber/thatch 금지**. 필요 시 `WallStyle.stone` + `RoofStyle.flat` + 작은 랜드마크만. **파괴 가능 캐시·통행 차단 타워는 기존 `BlockComponent` 유지.**

이미 게임이 같은 화해를 `WorldTree` 에서 증명했다 (`world_tree.dart:14–16`).

### 3.3 PC 이행 구조
**문제**: `HumanoidRenderer` 는 골격·포즈·클립 체계이고, 현재 `CyborgRenderer` 는 자체 `_View`/`_Levels` + 블레이드 홀스터 + 임플란트 디테일이다. API가 다르다.

**권고 어댑터**:
```text
// 개념 (구현 지시용 — 이 보고서는 코드를 쓰지 않음)
CyborgRenderer.drawBody(...)  // 시그니처 유지
  → 내부가 HumanoidRenderer.paint(pose, yaw, light) 로 위임
  → 또는 Feature flag: useProvisBody
```
- `CharacterBuild` 매핑 초안:
  - `assault` → `Archetype.paladin` 또는 `berserker`, `Sex.male`, `armorHeaviness: 0.9`, `muscle: 0.85`, `hasPauldrons: true`, palette = `playerArmor`/`playerAccent`/`playerSkin` (`cyborg_design.dart:178–217` + `recruits.dart` oreb/vant 패턴).
  - `infiltrator` → `Archetype.assassin`, `Sex.female`, `armorHeaviness: 0.35–0.55`, `hairLength` 높음, kestrel 패턴 (`recruits.dart:362–383`).
- **무기**: 인게임 블레이드는 `showBlade` + `_renderBladeSwing` 이 별도 (`player.dart:1229+`, `remote_player.dart:452`). provis `WeaponKind` 와 이중으로 그리면 칼이 두 자루. **1차 이식에서는 provis 무기를 `WeaponKind.none` 또는 미장착에 가깝게 두고 게임 스윙 이펙트를 유지**하는 편이 안전.
- **조명**: 밝은 월드이므로 `LightRig.heroic`/`spectral` 을 그대로 쓰면 ambient 가 어둡다 (`shading.dart:91–113`). 게임 쪽 `LightRig` 래퍼 — key 차갑고 밝게, ambient 를 `skyLow` 쪽으로, rim 을 `playerAccent` 계열.

### 3.4 맵 이행 구조
```text
[유지] LevelMap 데이터 · 통행 · hazard
[유지] GroundLayer 청크 Picture (플레이트·도관·격자)
[신규] PropDecorLayer (또는 bake 확장)
        - 카메라 가시 청크의 PropInstance 목록
        - 청크 단위로 ui.Picture 에 paintProp 결과 bake
        - walkable props 만 (장식) → LevelMap 충돌과 이중 관리 금지
[유지] BlockComponent / WorldTree / SafeZoneField
```
- `IsoSceneComponent.addProp` 이 grid 를 block 하는 동작 (`iso_scene.dart:128–132`) 을 게임 `LevelMap` 과 병행하면 **반드시 어긋난다.** 장식 prop 은 `walkable: true` 이거나 충돌을 LevelMap 에만 둔다.
- `paintIsoGround` (`iso_stage.dart:125`) 은 작은 맵 전체 재도색용 — 1 km 에 매 프레임 호출 금지.

### 3.5 성능 숫자
| 부하 | 계산 | 예산 대비 |
|---|---|---|
| PC 1 | 0.28–0.42 ms (provis README) | 1.7–2.5% of 16.6 ms |
| PC 20 (원격 포함) | **5.6–8.4 ms** | **34–51%** |
| + 몬스터 30 (적 자체 렌더 유지 가정) | 적 비용 별도, 이미 enemy 1,243줄 절차 렌더 | 여유 거의 없음 |
| Prop 100개를 매 프레임 | [추측] 기물당 수십~수백 µs → 수 ms | 청크 bake 없으면 위험 |

**필수 완화**
1. Prop 은 `GroundLayer` 와 같이 **청크 Picture bake** (정적·저주기).
2. 캐릭터 `detail` 거리 감쇠 (`HumanoidRenderer`/`paint` 의 detail 인자).
3. 원격 플레이어: 화면 가장자리는 임플란트 생략·저 detail.

## 4. 반례 · 대안 · 한계

### 채택하지 않은 대안
| 대안 | 버리는 이유 |
|---|---|
| A. 게임 전체를 provis 예제 아키텍처로 이전 | §0 가설 1. 1 km·AOI·24 Hz 동기화와 비호환. |
| B. 타일을 156×78 로 키워 provis 예제와 통일 | 줌·히트·이동 체감·청크 픽셀 크기 전면 재조정. 이득 대비 비용 과다. 기본 IsoView 가 이미 128. |
| C. 판타지 숲·목조 마을을 “멋진 맵”으로 직수입 | 세계관 정합성 실패 (`palette`/`GAME-DESIGN`). |
| D. 셰이딩만 영원히 | 맵이 장판으로 남는 핵심 약점 미해결. |
| E. 서버에 CharacterBuild JSON 저장 | 서버 원칙·현재 kind 화이트리스트 범위 초과. 외형은 클라이언트 해석이 맞고 kind 만 권위. |

### 한계 · 리스크
- provis **휴머노이드 기본형은 판타지 장비 어휘**(헬름·망토·룬). `glowRunes: true` 는 회로처럼 읽히게 재색 가능하나, **사이보그 고유 임플란트(흉골 프레임 등)** 는 `HumanoidRenderer` 에 없음 → 손그림 `Artist` 오버레이 또는 게임 쪽 디테일 패스 필요 [1차 이후].
- `BuildingProp` 의 중세 단위(기와·초가)는 사이버 톤에 한계 → **데이터 타워는 기존 block 개선이 더 정합**.
- 적(`enemy.dart`) 은 이번 범위에서 2순위. 아군만 예뻐지고 적이 구식이면 식별성은 유지되나 톤 분열.
- provis 패키지 수정 금지(지침) — `Finish` 사이버 전용 추가가 필요하면 **게임 래퍼에서 색/LightRig 로 우회** 우선.

### 문서-코드 괴리
- `GAME-DESIGN.md` 방향 불리언 vs 실제 연속 yaw → 이행·리뷰 시 코드 우선.

## 6. 불확실 · 미확인

1. **Humanoid 1인 실측 418 µs** 가 이 머신·release/debug·임플란트 오버레이 포함인지는 이 환경에서 재측정하지 못함. 숫자 인용은 provis README 기준. **통합 후 DevTools 로 N=1,10,30 재실측 필요.**
2. **Prop bake 비용** — 기물 종류·detail 별 µs 미실측. 1순위 구현 직후 청크 bake 시간 로그 필수.
3. **provis walk/run 클립** 이 게임 대시·밀리 스윙 팔 각도와 얼마나 맞는지 — 코드 경로만 확인, 시각 대조 미실시.
4. **BuildingProp 을 사이버 색만으로 “데이터 센터”로 읽히는지** — 단위 텍스처가 돌/벽돌이라 한계 가능. 랜드마크 소량 A/B 필요.
5. **원격 플레이어 상한** — AOI 내 동시 렌더 인원 실측치 미확인. 성능 표의 N=20 은 설계 가정.
6. **`Finish.energy` + 밝은 배경** 에서 가산 블렌드(`shading.dart:637`) 과다 노출 여부 — 스크린샷 튜닝 필요.
7. 형제 게임 라리엔 비주얼 관례는 읽지 않음 (지시상 참고 가능하나 이번 범위에서 필수 아님).

### 가설을 가르는 다음 증거 (구현 단계에서)
- 1순위 Prop 장식만 켠 스크린샷 vs 현재 → “맵이 지루한 판인가” 판정.
- 2순위 셰이딩 후 최소 줌 0.275 스냅샷 (`cyborg_render_snapshot_test.dart:40–45`) → 실루엣 생존 여부.
- 3순위 어댑터 후 선택 화면/인게임/원격 나란히 → 정체성 일치 여부.
- N명 프로파일 → 가설 “Humanoid 전면이 예산 내”의 가부.
